Цифровой архив театра

1. Описание проекта

Цифровой архив театра — веб-приложение для хранения и управления информацией о постановках, артистах, гастролях, фестивалях, конкурсах, документах и материалах театра.

2. Стек технологий

- Python 3.12
- Flask — веб-фреймворк
- SQLAlchemy (Flask-SQLAlchemy) — работа с базой данных
- SQLite — база данных
- Bootstrap — вёрстка интерфейса
- Jinja2 — шаблонизатор

3. Установка локально

3.1. Клонирование репозитория

```bash
git clone <URL репозитория>
cd theater_archive
```

3.2. Создание виртуального окружения

```bash
python -m venv venv
```

3.3. Активация виртуального окружения

Windows:
```bash
venv\Scripts\activate
```

Linux/macOS:
```bash
source venv/bin/activate
```

3.4. Установка зависимостей

```bash
pip install -r requirements.txt
```

3.5. Настройка переменных окружения

Скопируйте файл `.env.example` в `.env`:

```bash
copy .env.example .env      # Windows
cp .env.example .env        # Linux/macOS
```

Откройте `.env` и заполните:

- SECRET_KEY — ключ для подписи сессий Flask. Сгенерировать можно командой:
  ```bash
  python -c "import secrets; print(secrets.token_hex(32))"
  ```
  Если оставить пустым, ключ будет генерироваться заново при каждом запуске сервера, и все сессии пользователей будут сбрасываться при перезапуске.

- ADMIN_PASSWORD — пароль для встроенной учётной записи `admin`, создаваемой при первом запуске. Если оставить пустым, будет использован пароль по умолчанию `admin123`.

- DATABASE_PATH — полный путь к файлу SQLite.
- UPLOAD_FOLDER — полный путь к корню загруженных файлов.
- BACKUP_FOLDER — полный путь к каталогу резервных копий.

Пустые значения сохраняют прежнее поведение: база находится в
`instance/theater_archive.db`, файлы — в `uploads`, резервные копии — в `backups`
рядом с исходным кодом. Относительные пути разрешаются от каталога проекта, но
для сервера рекомендуется указывать полные пути.

3.6. Инициализация базы данных

```bash
python init_db.py
```

Эта команда применит миграции схемы и создаст базовые данные: роли пользователей и учётную запись администратора (если их ещё нет).

Для новой установки с вынесенными хранилищами вместо этой команды выполните
явную инициализацию (команда откажется перезаписывать существующую базу или
непустую папку файлов):

```powershell
python storage_tool.py initialize `
  --database C:\TheaterArchive\data\theater_archive.db `
  --uploads D:\TheaterArchive\uploads `
  --backups C:\TheaterArchive\backups
```

Для локальной проверки все три пути могут быть обычными папками на одном диске:

```powershell
python storage_tool.py initialize `
  --database C:\temp\theater-test\db\archive.db `
  --uploads C:\temp\theater-test\uploads `
  --backups C:\temp\theater-test\backups
```

3.7. Запуск приложения

```bash
python run.py
```

На Windows можно также воспользоваться файлом `start.bat` (двойной клик или запуск из консоли) — он сам вызовет `run.py`.

После запуска приложение будет доступно по адресу [http://localhost:5000](http://localhost:5000).

4. Перенос существующей базы и файлов

Перед переносом остановите веб-приложение. Не меняйте пути в `.env` вручную до
копирования. Из каталога проекта выполните:

```powershell
python storage_tool.py migrate `
  --database C:\TheaterArchive\data\theater_archive.db `
  --uploads D:\TheaterArchive\uploads `
  --backups C:\TheaterArchive\backups
```

Утилита делает проверенную резервную копию SQLite, копирует базу штатным SQLite
backup API, копирует дерево uploads с проверкой имён и размеров, сверяет все
`file_path` из базы и только после успешной проверки записывает новые абсолютные
пути в `.env`. Исходная база и исходный каталог uploads намеренно не удаляются:
удалять их следует вручную только после запуска и пользовательской проверки.

Полезные команды:

```powershell
python storage_tool.py status                 # пути, целостность БД и потерянные ссылки
python storage_tool.py backup                 # полная копия БД и uploads
python storage_tool.py backup --database-only # только согласованная копия SQLite
```

Команда `backup` всегда берёт место назначения из `BACKUP_FOLDER`. Она создаёт
там отдельный каталог `archive_ГГГГММДД_ЧЧММСС_...`, содержащий:

- `theater_archive.db` — согласованный снимок, созданный SQLite backup API;
- `uploads` — полное дерево загруженных файлов;
- `manifest.json` — список файлов, размеры и SHA-256 для проверки копии.

Приложение останавливать для создания копии не требуется. Во время снимка SQLite
остаётся доступной для чтения и записи. Новая загрузка файла может кратковременно
подождать окончания копирования uploads; это не позволяет получить в комплекте
частично записанный файл. После копирования утилита проверяет целостность БД,
контрольные суммы всех файлов и наличие каждого файла, на который ссылается БД.

### Восстановление полной копии

Сначала восстановите комплект в **новые** пути, не меняя рабочую конфигурацию:

```powershell
python storage_tool.py restore `
  --backup C:\TheaterArchive\backups\archive_20261001_120000_000000 `
  --database C:\restore-check\db\theater_archive.db `
  --uploads C:\restore-check\uploads
```

Команда сначала повторно проверяет manifest, БД и все файлы, собирает комплект во
временных путях и только затем публикует результат. Существующая БД не
перезаписывается, а непустой каталог uploads не принимается. Без `--activate`
файл `.env` не меняется — это безопасный режим пробного восстановления.

Для проверки восстановленного экземпляра можно временно задать переменные в
отдельном окне PowerShell и запустить приложение:

```powershell
New-Item -ItemType Directory -Force C:\restore-check\backups
$env:DATABASE_PATH = 'C:\restore-check\db\theater_archive.db'
$env:UPLOAD_FOLDER = 'C:\restore-check\uploads'
$env:BACKUP_FOLDER = 'C:\restore-check\backups'
python run.py
```

Откройте нужную карточку и её файл. После проверки остановите тестовый процесс и
закройте это окно PowerShell, чтобы временные переменные не влияли на обычный
запуск.

Для окончательного переключения остановите рабочее приложение и повторите
восстановление в новые постоянные пути с `--activate`:

```powershell
python storage_tool.py restore `
  --backup C:\TheaterArchive\backups\archive_20261001_120000_000000 `
  --database C:\TheaterArchive\restored\theater_archive.db `
  --uploads D:\TheaterArchive\restored-uploads `
  --backups C:\TheaterArchive\backups `
  --activate
```

После успешной проверки команда запишет новые пути в `.env`. Затем приложение
можно запустить обычным способом. Если требуется восстановить ровно в прежние
пути, сначала при остановленном приложении переименуйте повреждённую БД и папку
uploads для сохранности; утилита намеренно не удаляет и не перезаписывает их.

Копии `--database-only` не содержат uploads и поэтому не принимаются командой
полного восстановления. Ежедневные/инкрементные копии и удаление старых
комплектов этой командой не выполняются. Для этого предназначена отдельная
утилита ниже.

### Автоматический недельный и ежедневный цикл

Основная команда расписания не зависит от ОС:

```powershell
python scheduled_backup.py run
```

Её нужно запускать один раз в сутки. Первый запуск создаёт полный недельный
комплект. Следующие запуски создают ежедневные инкременты, а когда полному
комплекту исполняется семь дней — сначала создают и проверяют новый полный
комплект. Только после успешной повторной проверки нового комплекта удаляется
каталог предыдущей полной копии вместе со всеми относящимися к ней ежедневными
копиями. Ручные комплекты `archive_...`, созданные `storage_tool.py backup`, эта
ротация не затрагивает.

Структура хранится в `<BACKUP_FOLDER>/scheduled`:

- `set_.../full` — полная база, uploads и manifest;
- `set_.../daily/day_...` — согласованный снимок SQLite на этот день, новые и
  изменённые файлы, список удалённых файлов и полный снимок контрольных сумм;
- `set_manifest.json` — начало недельной цепочки и контрольные суммы её базы.

SQLite ежедневно сохраняется штатным Online Backup API. Файловый инкремент
учитывает добавление, изменение содержимого и удаление. Даже если файлы не
изменились, ежедневная точка содержит новое проверенное состояние базы.

Доступные даты восстановления:

```powershell
python scheduled_backup.py list
```

Безопасное пробное восстановление выбранного дня в новые пути:

```powershell
python scheduled_backup.py restore `
  --date 2026-10-03 `
  --database C:\restore-check\db\theater_archive.db `
  --uploads C:\restore-check\uploads
```

Утилита проверяет полную копию и каждый следующий инкремент, применяет их по
порядку, сверяет итоговые SHA-256 и ссылки из БД. Существующая БД и непустая
папка uploads не перезаписываются. После пользовательской проверки можно
остановить рабочее приложение и выполнить восстановление в новые постоянные
пути с `--backups ... --activate`, как для обычной полной копии.

Дополнительные ручные команды:

```powershell
python scheduled_backup.py full   # немедленно начать новую неделю и ротировать старую
python scheduled_backup.py daily  # создать очередную дневную точку
```

Параметр `--date YYYY-MM-DD` предназначен для тестирования или последовательного
восполнения пропущенных дат. В обычном расписании его указывать не нужно.

#### Настройка расписания на сервере

В планировщике конкретной ОС создайте **одну ежедневную задачу**, например на
02:00, запускающую `python scheduled_backup.py run`. Укажите полный путь к Python
виртуального окружения и к `scheduled_backup.py`. Учётная запись задачи должна
иметь чтение рабочей БД/uploads и запись в `BACKUP_FOLDER`. Первый успешный запуск
задаёт день недельного цикла; если один запуск пропущен, новая полная копия будет
создана при первом запуске после достижения семи дней.

Пример действия Windows Task Scheduler:

```text
Program: C:\TheaterArchive\.venv\Scripts\python.exe
Arguments: C:\TheaterArchive\scheduled_backup.py run
Start in: C:\TheaterArchive
```

Пример строки cron на Linux:

```text
0 2 * * * cd /opt/theater_archive && /opt/theater_archive/.venv/bin/python scheduled_backup.py run >> /var/log/theater-archive-backup.log 2>&1
```

Следует включить контроль кода завершения и журнала задачи: при любой ошибке
создания или проверки команда завершается ненулевым кодом, а предыдущий комплект
остаётся на месте. Также нужно контролировать свободное место в `BACKUP_FOLDER`.

Если данные уже были перенесены другим способом, их можно подключить без
копирования командой `configure` с теми же тремя аргументами. Она также не
примет конфигурацию, если база повреждена или какой-либо файл по ссылке из БД
отсутствует. При опечатке в явном пути приложение завершит запуск с понятной
ошибкой и не создаст пустую базу или пустую папку вместо данных.

5. Структура проекта

```
theater_archive/
├── app.py            — инициализация приложения, регистрация blueprints, базовые роуты
├── models.py         — модели базы данных (SQLAlchemy)
├── config.py         — настройки приложения
├── utils.py          — вспомогательные функции (загрузка файлов и т.п.)
├── migrations.py     — миграции базы данных
├── init_db.py        — инициализация БД: применяет миграции и сеет базовые данные
├── storage.py        — разрешение путей и защита от пустого хранилища
├── storage_tool.py   — настройка, перенос, проверка и резервное копирование
├── scheduled_backup.py — недельные полные и ежедневные инкрементные копии
├── run.py            — точка входа для запуска сервера
├── requirements.txt  — зависимости Python
├── routes/           — маршруты приложения (Flask blueprints)
├── templates/        — HTML-шаблоны (Jinja2)
├── static/           — статические файлы: CSS, JS, изображения
└── uploads/          — загружаемые пользователями файлы (в git не хранится)
```

6. Роли пользователей

- Администратор — полный доступ ко всем разделам, включая управление пользователями.
- Редактор архива — редактирование постановок, артистов и связанных данных.
- Завлит — доступ к редактированию либретто (помимо общих прав редактирования).
- Нотный библиотекарь — управление музыкальными материалами (клавиры, партитуры, фонограммы).
- Наблюдатель — только просмотр данных, без прав редактирования.

Администратор на странице «Управление → Права ролей» отдельно настраивает для
каждой роли:

- доступ к разделу формирования отчётов;
- скачивание сформированных отчётов Word и Excel;
- открытие и скачивание загруженных файлов архива.

Экспорт одновременно формирует документ и отдаёт файл, поэтому адреса экспорта
требуют обоих отчётных прав. Ограничения действуют и при прямом обращении к URL,
а не только скрывают элементы интерфейса. Права администратора на эту страницу,
отчёты и файлы отключить нельзя. Эти настройки не заменяют специальные правила:
редактирование, музыкальные материалы и либретто по-прежнему ограничиваются
исходными ролями.

7. Журнал действий

Администратор может открыть пункт «Журнал действий» в разделе «Управление».
Таблица журнала создаётся автоматически при следующем запуске `python run.py`.
Журнал сохраняет дату и время, пользователя, действие и понятный снимок объекта
для успешного создания, изменения и удаления данных, а также для формирования
отчётов. Снимок названия и ID сохраняется независимо от исходного объекта, поэтому
запись об удалении остаётся читаемой. Пароли и другие секреты в журнал не передаются.

Отдельной серверной функции печати в приложении сейчас нет. Нажатие `Ctrl+P` —
локальное действие браузера, которое приложение не может достоверно отследить и
не записывает в журнал.
